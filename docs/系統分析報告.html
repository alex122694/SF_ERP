SF ERP 系統分析報告人事出缺勤、請假扣款與特休管理系統：資料結構、技術棧與資料流

01 · SUMMARY

摘要

~7,000行程式碼與文件
3個執行期依賴
7張 SQLite 資料表
4次 schema migration
74 / 74個單元測試通過
1.26 MB單檔 index.html
  1. 這是一套「沒有伺服器的 Web 應用」。輕量版（lite）把 React 前端、規則引擎與 SQLite（sql.js WASM）全部打包成一個 index.html，用 Chrome／Edge 以 file:// 開啟，透過 File System Access API 直接讀寫使用者選定資料夾內的 sf_erp.sqlite。不開 port、不連網路，由 CSP 強制。
  2. 資料模型小而清楚。7 張表：員工、請假紀錄（一天一筆）、假別、特休結算、行事曆年度、行事曆日、系統設定。扣款金額與時數在存檔時算好寫入，其餘數字（特休剩餘、到期提醒、統計）都在畫面上即時推導，不另外存。
  3. 資料流是「整份讀出、整份寫回」。每次修改都在記憶體中的 SQLite 交易內完成，接著把整個資料庫 export 成位元組，經由「先寫暫存檔、close 時取代」的方式原子寫回磁碟；當天第一次存檔前先備份，保留 30 份。寫入失敗會把記憶體還原成上次成功存檔的內容。
  4. 規則集中在一個純函式模組。rules.ts（467 行）涵蓋工時重疊計算、扣款、勞基法 §38 特休週年制、遞延／換錢／歸零與所有防呆；同一個 checkLeave() 同時用於畫面即時試算與存檔檢查，兩者不會不一致。
  5. 品質基礎良好，但有幾處需要處理。TypeScript strict 編譯無錯、74 個測試全過。主要風險在：本機 node_modules 與宣告版本不符（vite 5 對 7）、跨語言規則測試案例只涵蓋計算函式、規格文件已落後實作、刪除員工會連帶刪除特休換錢紀錄。詳見第 10 節。
  6. 標準版仍停留在規格。規格描述的 Java 17 / Spring Boot 3 / PostgreSQL 16 / docker compose 版本在 repo 中沒有任何程式碼；前端已預留 DataSource 介面與 edition: 'std'，但尚無 ApiSource 實作。

05 · DATA MODEL

資料結構

SQLite schema 定義在 web/src/data/schema.ts，以陣列記錄 migration，開啟資料檔時依 PRAGMA user_version 逐一套用，每一步包在交易中。外鍵在每次開啟時以 PRAGMA foreign_keys = ON 啟用。日期一律存 YYYY-MM-DD 文字，避免時區問題。

實體關聯

實線為外鍵；虛線為程式邏輯上的對應（登記請假時以 calendar_day 判斷是否為放假日，但兩表之間沒有外鍵）。綠底表頭為核心業務表。

06 · DATAFLOW

Dataflow

lite 的資料流可以歸納成四條：開啟、寫入、行事曆匯入、匯出與移轉。讀取沒有獨立的流程，因為所有讀取都來自記憶體中的 State 快取，再由 derive.ts 與 rules.ts 在繪製時推導。

A. 開啟資料夾

1 · App檢查 showDirectoryPicker；不支援（非 Chrome／Edge）顯示說明畫面
2 · IndexedDB讀出上次的資料夾 handle，顯示「歡迎回來」
3 · 使用者點擊requestPermission({ mode: 'readwrite' })
4 · BroadcastChannel送出 hello，300 ms 內收到 busy 則以唯讀開啟
5 · .lock別台電腦 3 分鐘內有心跳 → 詢問唯讀或強制開啟
6 · loadSql把內嵌的 WASM data URL 解碼後初始化 sql.js
7 · Db.open讀 sf_erp.sqlite（沒有就新建）、套用 migration
8 · LiteSource快取 state()，進入 AppProvider

B. 登記一筆請假（寫入路徑）

所有寫入（員工、紀錄、行事曆、設定、特休處理、匯入）都走同一個 LiteSource.mutate()，以 Promise 佇列序列化，不會有兩個寫入同時進行。

#LeaveForm（畫面）LiteSourceDb ＋ rulesFolderStore磁碟
1每次輸入呼叫 checkLeave() 即時試算時數、扣款、特休剩餘
2假別開啟雙重確認時先顯示確認畫面
3run(() => src.saveLeave(f))排入寫入佇列；唯讀分頁直接拒絕
4state() 讀全表 → checkLeave() 再檢查一次
5INSERT，hours 與 deduction 一起寫入
6db.export() 取得整份位元組；更新快取並通知畫面
7讀舊檔；今天還沒有備份就寫 backup/sf_erp-YYYYMMDD.sqlite 並刪掉超過 30 份的backup/
8createWritable() 寫暫存檔，close() 時取代原檔sf_erp.sqlite
9側欄顯示「已自動儲存 · HH:MM」記下 lastSaved
9′紅色提示「存檔失敗，這次修改沒有存進資料檔」寫入失敗：用 lastSaved 重開 Db，快取還原

C. 匯入政府辦公日曆

1 · 檢查大小上限 10 MB
2 · unzipDecompressionStream('deflate-raw')，邊解邊計算，總量超過 50 MB 立即停止
3 · 解析 XMLsharedStrings、styles（fills／cellXfs）、sheet1；NFKC 正規化相容表意文字
4 · 年度標題「西元 XXXX 年」
5 · 放假底色圖例「放假日」左側的實心底色；找不到時任何實心底色都算
6 · 月曆方塊找出 12 個「日一二三四五六」標題列，逐格驗證日期與星期
7 · importCalendarUPSERT 該年每一天的 gov_holiday；override 不動

D. 匯出與移轉

員工主檔 → CSV

UTF-8 BOM、CRLF；以 = + - @ 開頭的文字前加單引號，避免 Excel 公式注入。

請假總覽 → Excel

自製單一工作表 xlsx：凍結標題列、置中換行、依行數設列高，標題與合計列加粗。

資料檔 → 標準版

「匯出給標準版」下載 lastSaved 位元組（application/vnd.sqlite3），供標準版管理者整批轉入空資料庫。

v1.2 db.json → lite

上限 20 MB；單一交易轉入，時數與扣款重算，比對筆數後回報結果。

立即備份

把 lastSaved 寫到當天的備份檔（同一天重複會覆蓋）並修剪舊備份。

v1.2 的流程（參考）

瀏覽器 fetch('/api/…') → server.js 驗證 → 修改記憶體中的 db 物件 → 暫存檔 rename 寫回 db.json。

一般假別：時數 ＝ 請假時段與兩段工作時段的重疊分鐘（午休不算），全天 7.5 h。特休例外：上午、下午各算 4 h、全天 8 h（v3 起）。遲到：從 09:30 起算實際分鐘，1～30 分。

金額公式（以整數分鐘計算，避免浮點誤差）
時薪 = 月薪 ÷ 30 ÷ 8 扣款 = round(分鐘 × 月薪 × (100 − 給薪%) ÷ (60 × 30 × 8 × 100)) 特休換錢 = round(分鐘 × 月薪 ÷ (60 × 30 × 8))

例：月薪 36,000、病假下午 300 分、給薪 50% → 扣 375 元（rules-cases.json 第 1 筆）。

選「遞延」時，遞延額度部分仍立即換錢，只有本期剩餘延到下一期。歸零會再提示可能違反 §38 第 4 項。結算後該期不能再登記特休。

checkLeave() 的檢查順序

  1. 日期格式
  2. 該年度已匯入行事曆，且不是放假日
  3. 已選員工，且當天在職
  4. 已選假別；生理假限女性
  5. 時間格式；遲到起 09:30 且 1～30 分
  6. 其他假別 30 分對齊、訖晚於起；特休只能三種時段
  7. 時數大於 0
  8. 同員工同日時段不重疊
  9. 特休：年資滿 6 個月、該期未結算、剩餘足夠
08 · SECURITY & INTEGRITY

安全與資料完整性

隔離與輸入防護
  • 建置時注入 CSP：default-src 'none'、connect-src 'none'，只允許內嵌腳本、樣式與 WASM；打包腳本確認沒有外部 <script src>。
  • 上傳大小上限：xlsx 10 MB、db.json 20 MB；xlsx 解壓總量 50 MB，邊解邊計算，不信任 zip 標頭。
  • 所有 SQL 以參數綁定執行；唯一字串拼接的是 schema 種子資料（來自程式常數）。
  • CSV 匯出防公式注入；i18n 查表用 Object.hasOwn，資料夾名稱等外部字串不會查到原型屬性。
  • v1.2 伺服器只綁 127.0.0.1，靜態檔路徑經 normalize 並限制在 public/ 內。
資料完整性
  • 寫入在 SQLite 交易中完成；tx() 支援巢狀，內層錯誤整批還原。
  • 磁碟寫入以 createWritable() 先寫暫存檔，close() 才取代，中斷不會損毀舊檔。
  • 存檔失敗時以上次成功的位元組重建 Db，畫面不會顯示沒存進去的資料。
  • 每日第一次存檔前備份，保留 30 份；整個 data/ 複製走即為完整備份。
  • 外鍵 CASCADE、CHECK 約束（性別、薪資 > 0、action 列舉）、UNIQUE（一期一筆結算）。
  • 同瀏覽器第二分頁強制唯讀；跨電腦以 .lock 心跳警告。

10 · FINDINGS

發現與風險

依影響程度排序。沒有發現會造成資料遺失或錯帳的程式錯誤；以下多為一致性、可維護性與規模上的問題。

F1

本機開發套件版本與宣告不符

中

npm ls：vite 5.4.11（宣告 ^7.3.7）、@vitejs/plugin-react 4.3.4（^5.2.0）、vite-plugin-singlefile 2.0.3（^2.3.4）、vitest 2.1.8（lock 為 4.1.11）。目前的測試通過與建置結果，不能代表 package.json 宣告的工具鏈。

建議在 web/ 執行 npm ci 後重跑測試與 npm run lite，確認 Vite 7 下單檔內嵌與 CSP 注入仍正常。

F2

跨語言規則測試案例只涵蓋計算函式

中

規格要求 TypeScript 與 Java 兩份規則通過同一份 rules-cases.json。目前案例只有 leaveMinutes、deduction、cashOut、annualDaysForYears、annualPeriod、seniority；最容易寫錯的 checkLeave 防呆順序、annualStatus 遞延扣用、settlementsDue 與 buildSettlement 都只寫在 TS 測試裡。

建議動工標準版前，把這四個函式的情境（含錯誤訊息代碼）搬進 JSON，讓 Java 端有同樣的驗收標準。

F4

刪除員工會一併刪除特休換錢紀錄

低已處理 10/21

annual_settlement.employee_id 為 ON DELETE CASCADE。規格只說刪除員工要連帶刪除「紀錄」；換錢金額會列入薪資加項，刪除後就無從查核。

處理改為以離職日處理：Db.deleteEmployee() 遇到有出缺勤或特休處理紀錄的員工會拒絕；畫面上按「刪除」時說明原因並提供「填寫離職日」。只有完全沒有紀錄的員工可以刪除。

F5

編輯舊紀錄時以「目前薪資」重算扣款

低已處理 10/21

Db.saveLeave() 編輯時呼叫 checkLeave()，以員工當下的 salary 重算 deduction。調薪後若修改調薪前的紀錄（例如只改理由），該筆扣款會變動。v1.2 行為相同，但 v1.2 註解寫明「薪資變動不回溯」。

處理migration v5 在 leave_record 新增 salary（登記當時的月本薪），編輯時以該值重算；改成別的員工才用該員工目前的薪資。既有紀錄以升級時的薪資補上。

F6

每次存檔的讀寫量隨資料量線性成長

低

一次寫入會：state() 全表讀取兩次（檢查前、寫入後）、export() 整份資料庫、讀出整份舊檔、讀出整份當日備份檔只為了判斷它是否存在、再整份寫回。以 50 名員工、每人每年 30 筆、10 年估算約 1.5 萬筆紀錄、數 MB，仍在可接受範圍。

建議短期可把「備份是否存在」改為 getFileHandle 不讀內容，並記住當天已備份；資料量明顯成長時再考慮增量讀取。

F7

多台電腦共用資料夾只有建議性鎖

低

.lock 每 60 秒心跳、3 分鐘失效，使用者可按「我確定沒有人在用」強制開啟；兩邊同時寫入時後存者覆蓋先存者。同瀏覽器的分頁判定只等 300 ms，兩個分頁幾乎同時開啟時可能都成為可寫入。規格已註明「同一時間只讓一台電腦開啟」。

建議存檔前比對檔案的 lastModified 與上次讀取時是否相同，不同就停止並提示，能把覆蓋變成可見的衝突。

F8

舊版程式仍是根目錄的預設啟動方式

資訊

根目錄 npm start 與 start.bat 仍啟動 v1.2；規則有兩份實作（public/shared/rules.js 與 web/src/rules/rules.ts），特休時數已經分歧（v1.2 以實際重疊的 2.5／5／7.5 h 計，v2.0 以 4／8 h 計）。

建議確認還有沒有人在用 v1.2；完成移轉後把它搬到 legacy/ 或移除，避免誤啟動舊版。

F9

標準版尚未開始

資訊

repo 中沒有 Java 專案、PostgreSQL migration、docker compose 或 ApiSource。前端已透過 DataSource 介面與 edition 欄位預留切換點；app-context 中部分功能（備份、資料夾資訊）直接依賴 LiteSource。

建議先定義 REST 介面與 ApiSource，以 F2 補強後的 JSON 案例驅動 Java 規則開發。
